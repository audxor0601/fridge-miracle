**이 표를 먼저 만든 이유**: 재작성인지 개선인지 판단하려면 기존 것의 실체부터 알아야 했다. 정리해 보니 동작하는 자산은 유통기한 긴급도 공식과 화면 흐름 정도였고 성능 지표는 전부 연출이었다. 그래서 2.0의 목표를 '기능 추가'가 아니라 **표시된 것과 실제가 일치하는 서비스 만들기**로 잡았다.

</details>

<details>
<summary><b>"Random Forest 88.4% / XGBoost MAE 4.12 → <code>Math.random()</code> 출력 → 삭제"</b>가 무슨 뜻인가 (비전공자용 설명)</summary>

**용어부터**
- **Random Forest / XGBoost** — 머신러닝 알고리즘 이름. 앞은 분류(이 요리가 한식이냐 양식이냐), 뒤는 예측(영양 점수 몇 점이냐)에 쓴다.
- **88.4%** — 분류 정확도. 100번 중 88번을 맞혔다는 뜻.
- **MAE 4.12** — 평균 절대 오차. 예측한 점수가 실제와 평균 4.12점 차이났다는 뜻.

**그런데 1.0에서는**

이 숫자들이 나오려면 데이터를 모으고, 모델을 학습시키고, 시험 데이터로 채점하는 과정이 있어야 한다. 1.0에는 그 과정이 없었다. 화면의 숫자는 `Math.random()` — **난수 생성 함수**가 만들어낸 값이었다. 버튼을 누를 때마다 다른 숫자가 나오고, 새로고침하면 또 바뀐다. 옆에 뜨던 "ML 분석 중..." 로딩도 실제 계산이 아니라 1.2초 기다렸다가 다음 화면을 보여주는 연출(`setTimeout`)이었다.

비유하자면 **온도계를 달지 않고 온도계 그림에 숫자를 적어 넣은 것**에 가깝다. 화면은 그럴듯하지만 그 숫자가 가리키는 실제 측정은 없다.

**그게 잘못이었나**

당시 목적을 생각하면 아니다. 1.0은 학교 과제의 *설계서 검토용 프로토타입*이었고, "이런 화면과 이런 지표를 만들 계획"임을 보여주는 게 목적이었다. 목업에서 가짜 데이터를 쓰는 건 정상이다.

**그럼 왜 삭제하나**

용도가 달라지기 때문이다. 포트폴리오는 "내가 실제로 만든 것"을 증명하는 물건인데, 근거 없는 성능 수치가 하나라도 섞여 있으면 나머지 진짜 작업까지 의심받는다. 면접에서 "이 88.4%는 어떻게 나온 값이죠?"라는 질문 한 번이면 끝난다.

그래서 2.0에서는 **지어낸 숫자를 지우고, 실제로 측정한 값만 남긴다.** 수집한 레시피 건수, 재료 파싱 정확도, 추천 응답 시간 — 전부 직접 세고 재서 나온 숫자다. 없는 것을 있는 척하는 대신, 실제로 있는 것을 정확히 보여주는 쪽을 택했다.

</details>

## 1. 2.0 목표와 범위

**한 줄 정의** — 내 냉장고 재고를 등록해두면, 유통기한이 급한 재료부터 소비하도록 실제 레시피를 추천하고, 상하기 전에 알려주는 웹 서비스.

### 범위에 있는 것 (MVP)
- 이메일 회원가입 / 로그인
- 재고 등록·수정·삭제 (재료명, 수량, 구매일, 유통기한)
- 유통기한 D-day 대시보드 (인앱 배지)
- 보유 재료 기반 레시피 추천 (규칙 기반 + 유통기한 가중치)
- 매일 아침 이메일 다이제스트 ("오늘 3개 재료가 만료됩니다")

### 범위 밖 (명시적 제외)
- 머신러닝 모델 학습 — 실사용 데이터가 쌓인 뒤 2단계
- 웹 푸시 알림, 소셜 로그인, 바코드 스캔, 가족 공유
- 이미지 인식 재료 등록

경계를 문서에 박아두는 이유: 범위가 흐려지면 완성이 안 되고, 미완성 포트폴리오는 감점이다.

## 4. 추천 엔진 명세 (규칙 기반)

가짜 ML을 걷어낸 자리에 들어갈 **설명 가능한 공식**.

### 4.1 긴급도
```
urgency(i) = 1 / (남은일수 + 1)      # 1.0에서 계승
남은일수 < 0  → 만료, 추천 대상에서 제외하고 '폐기 후보'로 분리
남은일수 = 0  → urgency 1.00 (D-day)
남은일수 = 3  → urgency 0.25
```

### 4.2 레시피 점수

> **개정 이력** — 아래 v1 공식은 실제 재고로 돌려보고 버렸다. 세 번 고쳐 v4가 됐다.
> 버린 이유를 지우지 않고 남겨둔다. 왜 이 모양이 됐는지가 이 프로젝트의 내용이다.

#### v1 (설계 시점) — 폐기

```
coverage(r) = |H(r)| / |E(r)|
urgency_norm(r) = min(Σ urgency(H) / |E(r)|, 1)
score(r) = 100 × (0.65 × coverage + 0.35 × urgency_norm)
하드 필터: coverage < 0.5 제외
```

**폐기 사유**: 재료 9개를 넣었는데 추천이 0건이었다. 레시피당 필수재료가
평균 8.7개라 coverage 50%를 넘기려면 5개 이상이 겹쳐야 하는데, 1,152건 중
그런 레시피가 하나도 없었다. 설계 시점에 몰랐던 건 이 평균값이다.

#### v2 — 폐기

하한을 없애고 부족 재료 **개수**로 정렬했다. `된장 두부찌개`가 탈락했다.
청양고추 10g과 두부 320g을 똑같이 "부족 1개"로 세고 있었다.

#### v3 — 폐기

중량으로 주재료와 곁가지를 갈랐다(`MAIN_SHARE = 5%`). 목록과 상세의 보유
판정이 달라서, 대패삼겹살을 가지고 있는데 "살 것: 통삼겹"이 떴다.
판정을 `getOwnedMap()` 한 곳으로 모으고 같은 카테고리 육류를 대체 가능으로 묶었다.

#### v4 (현재)

```
주재료 = 레시피 전체 중량의 MAIN_SHARE(5%) 이상을 차지하는 재료
곁가지 = 나머지

제외: 주재료를 MAX_MISSING_MAIN(2)개보다 많이 사야 하는 레시피
제외: 내 재료를 하나도 안 쓰는 레시피
제외: 기한이 지난 재료 (4.1의 원칙 — v3까지 지키지 않았다)

정렬: ① 부족한 주재료 수 오름차순
      ② 보유 중량 비율 내림차순
      ③ 쓰는 재료의 평균 긴급도 내림차순
```

보유 판정 확장 (`expandPantry`):

- **물 성격**: 쌀뜨물·육수·채수는 가지고 있다고 본다. 소비 목록에는 넣지 않는다
- **접미사**: `대패삼겹살`은 `삼겹살`로 끝나므로 삼겹살로도 친다.
  한 글자 이름은 `무 → 무화과` 같은 오탐을 부르므로 제외
- **카테고리**: 레시피가 `돼지고기`처럼 뭉뚱그려 적으면 같은 카테고리 재고로 대신 센다.
  해물류는 넣지 않았다 — 새우 자리에 오징어를 넣으면 다른 음식이 된다

**4.1의 만료 처리를 v3까지 지키지 않았다.** `urgency`가 기한 지남에 1을 돌려주는
구현을 그대로 쓴 결과, 8일 지난 순두부가 추천 1순위로 올라왔다. 설계서는 맞았고
구현이 안 따랐다. 지금은 `getOwnedMap()`에서 갈라내고 냉장고 화면이 폐기를 안내한다.

### 4.3 화면에 보여줄 근거

"매칭률 75%" 한 줄로 끝내지 않는다. 설명 가능성이 규칙 기반을 선택한 이유이므로
그 이점을 화면에서 보여줘야 한다. 구현은 두 층으로 나눴다.

**목록 상단 요약** — 이 서비스가 대신 해준 일을 한 줄로 적는다.

> 재료 4개로 레시피 1,156개를 맞춰봤습니다. 기한이 지난 2개는 계산에서 뺐습니다.
> 내 재료가 들어가는 건 598개, 그중 가장 많이 겹치는 200개를 중량까지 따져보니
> 주재료를 2개 이내만 사면 되는 건 11개였습니다.
> 그 11개를 ① 살 주재료가 적은 순 ② 이미 가진 중량이 많은 순
> ③ 유통기한이 급한 재료를 쓰는 순으로 늘어놓았습니다.

숫자는 전부 `recommend()`가 그 순간 조회·계산한 값이다. 정렬 문구는 `scoreRecipes`의
실제 순서를 그대로 적는다. 처음에는 "급한 재료를 먼저 쓰는 순"이라고 썼는데,
유통기한은 1순위가 아니라 3순위 동점 처리다. 화면이 실제 동작과 다른 말을 하면 안 된다.

"상위 200개"를 굳이 문장에 드러낸 것도 같은 이유다. 엔진은 매칭 수 상위
`CANDIDATE_LIMIT`개만 중량 계산을 한다. 이걸 뭉개고 "1,156개 중 11개"라고 쓰면
1.0의 `Math.random()` 지표와 같은 종류의 문장이 된다.

**카드별 근거** — `살 것: 돼지고기, 김치` / `적게 들어가는 재료: 청양고추, 홍고추` /
쓰는 재료를 D-day와 함께 태그로.

### 4.4 조리 영상 연결 — 링크, API 아님

주부 사용자가 레시피를 보고 실제로 만들 때 유튜브를 함께 보는 경우가 많다.
YouTube Data API v3 도입 여부를 공식 문서 기준으로 검토했다.

| 사실 | 값 |
|---|---|
| 기본 쿼터 | `search.list` 100회/일 (그 외 엔드포인트 합산 10,000 units/일) |
| 검색 1회 비용 | 1 unit |
| 비인증 공개 데이터 캐시 | 최대 30일 |
| 재생 | YouTube 플레이어 필수 |

**결론: API를 쓰지 않는다.** 하루 100회 검색은 사용자 한 명이 레시피 100개를
열면 끝난다. 쿼터 증액은 신청·심사 대상이고, 30일 캐시 제한 때문에 결과를
DB에 쌓아두는 우회도 막혀 있다. 포트폴리오가 감당할 운영 부담이 아니다.

대신 레시피 상세의 조리 단계 위에 검색 링크 배너를 둔다
(`youtube.com/results?search_query=<요리명> 만들기`). 키도 쿼터도 ToS 노출도 없다.
검색어를 만드는 `youtube.ts`는 그대로 두었으므로, 나중에 API를 붙이면 재사용된다.

요리명은 원문 그대로 쓰지 않는다. `저염 황태해장국`은 `황태해장국`으로 줄인다.
「A와 B」 형태 제목은 규칙으로 자르려다 **사과**의 `과`를 매칭해
`순두부 사과 소스 오이무침`을 `순두부 사`로 만들었다. 규칙을 버리고 해당 10건은
수동 매핑으로 처리했다.

### 4.5 실측 지표 페이지 `/about`

1.0 화면의 `Random Forest 88.4%`를 만든 코드는 `Math.random()`이었다.
2.0은 지표를 띄우는 대신 **지표가 어디서 나왔는지를 같이 띄운다.**

화면의 모든 숫자는 둘 중 하나다.

- `scripts/build_metrics.py`가 원본 파일을 직접 세어 커밋한 `src/data/metrics.json`
- 페이지를 열 때 Supabase에 실제로 물어본 값

섹션마다 출처 스크립트명을 붙이고, 맨 아래에 재현 명령을 적었다.

파싱 검증은 두 가지를 따로 센다.

1. **원문 대조** — 이름이 원문에 글자 그대로 있는가 (파서가 지어내거나 잘라먹었나)
2. **잔재 검사** — 이름에 수량·괄호·콜론 찌꺼기가 남았는가 (자를 자리를 맞게 잘랐나)

처음에는 1번만 만들었고 99.91%가 나왔다. 그 안에 `마늘 1`, `녹차(티백,` 같은
이름이 293개 섞여 있었다. `마늘 1`은 원문에 그대로 있으니 1번을 통과한다.
2번을 따로 만들었고, 1번만 있었을 때 무엇을 놓쳤는지도 화면에 적었다.

## 5. 유통기한 알림 파이프라인

```
Supabase Cron (매시 정각, pg_cron)
  └─ Edge Function: expiry-digest
       ├─ x-digest-secret 헤더 확인
       ├─ notify_email = true 이고 notify_hour = 현재 KST 시각인 프로필 조회
       ├─ 오늘 이미 보낸 기록(notification_log)이 있으면 건너뜀
       ├─ storage_items 중 status='active' 이고 expires_on ≤ today+3 인 행 집계
       │    → 한 건도 없으면 메일을 보내지 않는다
       └─ Resend 발송 → notification_log 기록
```

인앱 배지는 별도 배치 없이 재고 조회 시 `expires_on`으로 즉시 계산한다.

### 5.1 시간대

Supabase는 UTC, 사용자는 KST(UTC+9). 매시 실행하고 사용자별 `notify_hour`를
현재 KST 시각과 비교한다. `sent_on` 판정에 쓰는 '오늘'도 KST 기준이다.
UTC 날짜를 쓰면 한국 시간 오전 9시가 전날로 계산돼 중복 발송이 난다.

### 5.2 보낼 게 없으면 보내지 않는다

급한 재료가 0건이면 메일을 만들지 않는다. "오늘은 임박한 재료가 없습니다"를
매일 보내면 사람은 며칠 만에 열지 않게 되고, 정작 필요한 날의 메일도 같이
묻힌다. 알림의 가치는 빈도가 아니라 열어볼 확률이다.

### 5.3 메일에 추천 레시피를 넣지 않는 이유 (v1)

설계 초안에는 "추천 레시피 상위 3개"를 메일에 싣기로 적어놨다. 빼기로 했다.

추천 엔진(`src/lib/recommend.ts`)은 브라우저에서 도는 코드다. Edge Function은
Deno 런타임이라 같은 파일을 그대로 못 쓰고, 복사해 넣으면 두 벌이 된다.
한쪽만 고치는 날 메일과 화면이 다른 요리를 말하게 된다. 이 프로젝트가
1.0에서 걷어내려던 게 정확히 그 어긋남이다.

그래서 v1의 메일은 급한 재료만 알리고 `/recipes` 링크를 건다. 추천은 화면
한 곳에서만 계산한다. 나중에 엔진을 순수 함수로 떼어내 양쪽이 같은 파일을
import 하게 되면 그때 넣는다.

### 5.4 Resend 도메인 제약 (확인된 사실)

Resend는 도메인 인증 전까지 **Resend 계정 소유자 본인 주소로만** 발송을
허용한다. 다른 수신자에게 보내면 403이 돌아온다. 공식 문서에 그렇게 적혀 있다.

이 프로젝트는 도메인을 사지 않았으므로, 지금 다이제스트는 개발자 본인 계정
하나에만 도착한다. 파이프라인(스케줄 → 조회 → 발송 → 기록)은 전부 실제로
동작하고, 수신자 범위만 막혀 있는 상태다. 화면과 README에 이대로 적는다.
"메일 알림 기능 구현"이라고만 쓰고 이 제약을 숨기면 1.0의 88.4%와 같은
종류의 문장이 된다.

### 5.5 이 기능이 스스로 만드는 지표

`/waste`의 '기한이 지난 뒤 버림 · 평균 N일 늦게'가 이 알림의 목표 숫자다.
알림을 켜기 전과 후의 N을 비교하면 효과를 실측으로 말할 수 있다.
지어낸 KPI가 아니라 서비스가 이미 기록하고 있던 값이다.

## 6. 외부 데이터 수집 (실제 데이터 검증의 핵심)

**소스**: 식품의약품안전처 「조리식품의 레시피 DB」(COOKRCP01), 무료·이용허락범위 제한 없음, JSON 제공

**파이프라인**
1. 공공데이터포털에서 키 발급 → 전체 페이지 순회 수집 → 원본 JSON 보관
2. `recipes` / `recipe_steps` 적재 (MANUAL01~20 중 빈 칸 제거)
3. `RCP_PARTS_DTLS` 파싱 → `recipe_ingredients`

**최대 난관은 3번이다.** 원문이 `"돼지고기 100g, 양파 1/2개, 진간장 2큰술"` 같은 자유 텍스트라 구분자도 단위 표기도 일정하지 않다. 계획:
- 구분자 후보(`,` `·` 개행)로 1차 분해
- 정규식으로 `수량 + 단위` 추출 (`1/2`, `2큰술`, `100g`, `약간`)
- 재료명은 `ingredients.aliases` 사전으로 표준명 매핑
- 매칭 실패 항목은 NULL로 남기고 **실패 목록을 파일로 출력** — 사전을 채우는 근거로 사용

**검증 기준 (이 단계의 완료 정의)**
- 수집 건수와 결측률 리포트 출력
- 무작위 30건을 원문과 눈으로 대조해 파싱 정확도 측정, **85% 이상**이면 통과
- 미달 시 사전 보강 후 재측정 — 이 반복 과정을 기록으로 남긴다

## 9. 막힐 것으로 예상되는 지점

미리 표시해 둔다. 실제로 부딪히면 **마스터 본인 문장으로** 아래에 채운다 — 이 항목이 면접에서 가장 많이 질문받는 부분이다.

1. **재료명 정규화** — "대파 / 파 / 쪽파"를 어디까지 같다고 볼 것인가. 사전을 어떻게 만들 것인가
2. **RLS 정책 디버깅** — 정책이 틀리면 에러가 아니라 "빈 배열"이 온다. 원인 찾기가 까다롭다
3. **Edge Function 시간대** — UTC/KST 혼선으로 발송 시각이 9시간 어긋나는 문제
4. **추천 가중치** — 0.65/0.35가 맞는 값인지 판단할 기준
5. **공공 API 응답 형식** — 페이지네이션 한도, 결측 필드 처리
