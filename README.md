# 냉장고의기적 2.0

냉장고 재고를 등록해두면, 유통기한이 급한 재료부터 소비하도록 실제 레시피를 추천하고 상하기 전에 알려주는 웹 서비스.

**배포 주소** → https://fridge-miracle.vercel.app

레시피는 식품의약품안전처 조리식품 레시피 DB 1,156건을 직접 수집·파싱해서 쓴다.
화면에 뜨는 지표가 어디서 나온 숫자인지는 [/about](https://fridge-miracle.vercel.app/about) 에서 확인할 수 있다.

## 왜 2.0인가

1.0은 학교 과제로 만든 설계서 검토용 프로토타입이었다. 화면에는 "Random Forest 정확도 88.4%"가 떠 있었지만 실제로는 `Math.random()`이 만든 숫자였고, 데이터는 상수 4건에 새로고침하면 사라졌다.

2.0의 목표는 기능 추가가 아니라 **화면에 표시된 것과 실제 동작이 일치하는 서비스**를 만드는 것이다.

| | 1.0 | 2.0 |
|---|---|---|
| 데이터 | 상수 4건, 새로고침 시 소멸 | Supabase Postgres |
| 레시피 | 하드코딩 배열 | 식약처 공공 API 수집·정제 |
| 추천 | `Math.random()` | 규칙 기반 + 유통기한 가중치 (설명 가능) |
| 사용자 | 없음 | 이메일 인증 + RLS 격리 |
| 성능 지표 | 지어낸 수치 | 실측치만 게시 |

## 기술 스택

- **프론트**: React 19, Vite, TypeScript, Tailwind CSS v4
- **백엔드**: Supabase (Postgres, Auth, RLS, Edge Functions)
- **데이터 수집**: Python (식약처 조리식품 레시피 DB, COOKRCP01)
- **배포**: Vercel

## 추천 규칙

설계서에 적었던 커버리지 가중합은 실제 재고로 돌려보고 버렸다. 세 번 고쳐서 지금은 이렇다.

```
주재료 = 레시피 전체 중량의 5% 이상을 차지하는 재료
곁가지 = 나머지 (청양고추 10g 같은 것)

주재료를 3개 이상 사야 하면 오늘 해먹을 수 없다고 보고 제외한다.
남은 것을 ① 살 주재료가 적은 순 ② 이미 가진 중량이 많은 순
                ③ 유통기한이 급한 재료를 쓰는 순으로 정렬한다.
```

- 소금·간장 같은 상비 양념과 쌀뜨물·육수는 가지고 있다고 계산한다
- 레시피가 `돼지고기`처럼 뭉뚱그려 적으면 같은 카테고리 재고(대패삼겹살)로 대신 센다
- **기한이 지난 재료는 계산에서 뺀다.** 1.0의 `urgency = 1/(남은일수+1)`은 기한이
  지나면 1을 돌려주는데, 그대로 두면 8일 지난 순두부를 1순위로 추천한다

버린 규칙과 버린 이유는 `src/lib/recommend.ts` 상단 주석에 남겨뒀다.

## 로컬 실행

```bash
npm install
npm run dev
```

`.env.local` 에 `VITE_SUPABASE_URL` 과 `VITE_SUPABASE_ANON_KEY` 가 필요하다.
anon 키는 공개되어도 된다 — 데이터를 지키는 건 RLS 정책이다.

### 데이터 파이프라인

레시피 DB를 처음부터 다시 만들 때의 순서. 각 단계는 여러 번 돌려도 결과가 같다.

```bash
python3 scripts/fetch_recipes.py        # 식약처 API에서 원본 수집
python3 scripts/parse_ingredients.py    # 재료 문장 분해
python3 scripts/load_to_supabase.py     # DB 적재
python3 scripts/clean_ingredients.py    # 사전 정제  (--apply 없이 미리보기 먼저)
python3 scripts/categorize_ingredients.py  # 카테고리 분류        (〃)
python3 scripts/prune_ingredients.py    # 안 쓰이는 재료 정리      (〃)
python3 scripts/build_metrics.py        # /about 지표 재생성
```

DB를 바꾸는 스크립트는 기본이 미리보기다. 출력을 눈으로 확인한 뒤에만 `--apply` 를 붙인다.

### 1. 테스트는 전부 통과했는데, 사실 아무것도 검사하지 않고 있었다

RLS 정책을 적용하고 로컬 Postgres에 사용자 두 명을 만들어 격리를 확인했는데, 만든 시나리오가 하나도 빠짐없이 통과로 나왔다. 그중 "B가 A의 재고를 조회"까지 통과라는 게 걸렸다. 차단돼야 맞는 항목이었다.

출력을 위에서부터 다시 읽으니 `WARNING: SET LOCAL can only be used in transaction blocks`가 있었다. `set local role authenticated`는 트랜잭션 밖에서 무시되기 때문에 모든 쿼리가 superuser 권한으로 돌아갔고, superuser는 애초에 RLS를 건너뛴다. 검사가 통과한 게 아니라 검사 자체가 없었다.

시나리오를 하나씩 `begin; ... commit;`으로 감싸고 다시 돌리자 그제야 차단이 걸렸다. 그 뒤로는 통과 표시를 믿기 전에 실패해야 할 케이스가 실제로 실패하는지부터 본다.

### 2. 파서가 생선살을 "선살"로 만들었다

"다진", "채썬" 같은 조리 상태 수식어를 재료명에서 떼는 규칙을 만들면서 "생"도 목록에 넣었다. 생새우와 생고기를 새우, 고기로 합칠 생각이었다.

무작위 30건을 뽑아 원문과 파싱 결과를 나란히 놓은 표를 만들었더니 첫 레시피부터 `생선살(100g)`이 선살로 들어가 있었다. 생강은 강, 생크림은 크림.

같은 표에서 두 개가 더 나왔다. 재료명이 두 글자 이상이어야 한다는 조건 탓에 물, 무, 배, 쌀이 통째로 사라졌고, `물 300ml(1½컵, 200g)`처럼 괄호 안에 쉼표가 있으면 항목이 중간에서 잘려 `120g)` 같은 조각만 남았다.

한 글자 재료는 에러도 안 나고 조용히 빠진다. 최종 결과만 봤으면 셋 다 놓쳤다.

### 3. 리눅스에서 설치한 node_modules를 맥에서 쓸 수 없었다

`npm run dev`를 실행하니 `Cannot find module '@rolldown/binding-darwin-arm64'`. 패키지는 분명히 설치돼 있는데 없다고 했다.

Vite와 Tailwind는 속도를 위해 OS별로 컴파일된 실행 파일을 같이 설치하는데, `npm install`을 리눅스 환경에서 돌린 탓에 리눅스용 바이너리만 깔려 있었다. 자바스크립트 패키지라도 이런 것들은 OS를 가린다. `node_modules`와 `package-lock.json`을 지우고 맥에서 다시 설치하니 바로 떴다. `node_modules`가 왜 `.gitignore`에 들어가는지 이때 알았고, 맥과 윈도우를 오가는 프로젝트라 저장소를 옮길 때마다 새로 설치하는 걸 규칙으로 잡았다.

### 4. 같은 실수를 방향만 바꿔 또 했다

재료 사전에 `마늘다진것`, `참치(캔,`, `양념]고추장` 같은 이름이 남아 있었다. 실제로 재고를 넣어보고 화면에서 보고서야 알았다. 추천은 `ingredient_id`로 조인하기 때문에 `마늘`과 `마늘다진것`이 다른 행이면 매칭이 안 된다.

규칙을 만들어 1,936개를 1,594개로 정리했다. 그 과정에서 세 번을 되돌렸다. 처음에는 `• [추가 재료] 쌈두부`가 `•`가 됐고(괄호 뒤가 재료인 경우를 빼먹음), 다음에는 `소금 0.25`가 `소금 0.`이 됐다(소수점). 마지막에는 `간`을 수식어로 넣었다가 `간편 어간장`이 `편 어간장`이 됐다.

세 번째가 뼈아팠다. 파서를 만들 때 `생`이 `생선살`을 `선살`로 만든 것과 완전히 같은 실수다. 한 글자 수식어는 단어 경계를 확인해야 한다는 걸 알고 있었는데도 또 했다. 이번에는 한 글자일 때만 뒤에 공백을 요구하도록 고쳤고, 망가진 이름 4개는 복구 스크립트를 따로 만들어 되돌렸다.

배운 건 규칙보다 순서다. 미리보기로 먼저 보고, 눈으로 확인한 뒤에 적용한다. 세 번 다 미리보기에서 잡았다면 DB를 건드릴 일이 없었다.

### 5. 내가 만든 검사가 통과라고 했는데, 틀린 걸 묻고 있었다

파싱이 맞는지 확인할 방법이 필요했다. 무작위 30건을 원문과 대조하는 표를 만들어뒀는데 판정란을 끝내 못 채웠다. 빈 칸으로 남은 표는 쓸 데가 없다.

그래서 자동으로 셀 수 있는 걸 만들었다. 파싱한 재료 이름 12,991줄이 각자 자기 레시피 원문에 글자 그대로 들어 있는지 전수 대조한다. `생선살`을 `선살`로 자르면 여기 걸린다. 통과율 99.91%, 실패 12줄이 나왔고 그 12줄을 `/about`에 띄웠다.

12줄을 고치려고 사전을 훑다가 이상한 걸 봤다. `마늘 1`, `설탕 2`, `배추김치 30`. 숫자로 끝나는 이름이 174개였다. 내 검사는 이걸 전부 통과시켰다. 원문에 "마늘 1"이 글자 그대로 있으니까.

파서가 없는 글자를 지어냈는지는 봤는데, 자를 자리를 맞게 잘랐는지는 안 봤다. 다시 세니 깨진 이름이 12개가 아니라 293개였다.

원인은 두 개였다. 수량 정규식이 괄호 안을 먼저 잡아서 `녹차(티백, 1개)`의 `1개`를 수량으로 쓰고 이름을 `녹차(티백,` 에서 끊었다. 그리고 `배추김치(줄기부분) 30`처럼 단위 없이 숫자만 적힌 경우를 수량으로 인정하지 않아 숫자가 이름에 눌러앉았다. 뒤쪽이 더 나빴다. 원문에 적혀 있던 수량 195개를 버리고 있었고, 추천 엔진은 그 자리를 기본값 30g으로 채우고 있었다. 알고 있던 값 대신 추측을 쓴 셈이다.

괄호 안을 가린 사본에서 수량을 먼저 찾도록 바꾸고, 단위 없는 끝자리 숫자도 수량으로 받게 했다. 293개가 1개로 줄었다. 남은 1줄은 식약처 원본이 `물(15m)`으로 적힌 오타라 손대지 않았다.

검사를 하나 더 만들었다. 이름에 수량, 괄호, 콜론이 남았는지 보는 검사다. `/about`에 두 지표를 나란히 놓고, 첫 번째만 있었을 때 293개를 못 봤다는 것도 그 자리에 적었다.

### 6. 8일 지난 순두부로 찌개를 끓이라고 추천했다

재고를 넣어두고 며칠 뒤에 추천 화면을 열었더니 이렇게 떠 있었다.

> 지금 가장 급한 건 순두부 8일 지남입니다.
> 된장 두부찌개 / 순두부 8일 지남, 마늘 10일 지남

카드 11개가 전부 상한 재료를 쓰라고 하고 있었다.

1.0에서 그대로 가져온 공식 탓이다.

```ts
urgency = 1 / (남은일수 + 1)
if (남은일수 < 0) return 1   // 기한 지남 = 가장 급함
```

기한이 가까울수록 급하다는 규칙을 끝까지 밀면 이미 지난 건 제일 급하다가 된다. 수식으로는 자연스럽다. 먹는 서비스에서는 틀린 답이다.

그다음이 민망했다. 설계서 4.1을 열어보니 이렇게 적혀 있었다.

> 남은일수 < 0 → 만료, 추천 대상에서 제외하고 '폐기 후보'로 분리

내가 쓴 문장이다. 설계는 맞았고 구현이 안 따랐다. 추천 엔진을 만들면서 설계서의 점수 공식은 실제 재고로 돌려보고 버렸는데, 그 옆줄까지 같이 흘려보냈다. 공식을 바꾼다고 경계 조건이 무효가 되는 건 아니었다.

기한 지난 재료를 추천 계산에서 빼고, 냉장고 화면 위에 따로 모아 폐기를 안내하게 했다. 계산에서만 빼면 버려야 할 게 있다는 사실까지 화면에서 사라진다. 배너 문구는 "버리세요"가 아니라 "실제로 버리셨다면 기록해 두세요"로 했다. 아직 냉장고에 있는데 앱이 마음대로 버림 처리할 수는 없다.

`d < 0 → 1` 코드는 지우지 않고 주석으로 남겼다.

### 7. 같은 자리에서 또 미끄러졌다

버림 기록 화면을 만들고 브라우저로 열었더니 이렇게 떠 있었다.

> 버린 재료는 유통기한이 지나고 평균 -7.0일 뒤에 처리했습니다

쪽파는 기한이 9월 21일인데 9월 14일에 버렸다. 기한 7일 전에 버린 것이다. 부호를 안 보고 전부 한 평균에 넣었다.

기한이 지난 뒤 버린 것과 오기 전에 버린 것은 뜻이 다르다. 앞쪽은 늦게 알아챈 것이라 알림이 할 일이 있고, 뒤쪽은 상했거나 안 먹을 것 같아서 버린 것이라 알림과 상관없다. 둘을 나눠서 따로 센다.

같은 확인에서 하나 더 걸렸다. 기록 1건으로 평균을 내고 있었다. 비율에는 10건 규칙을 걸어놓고 평균에는 안 걸었다. 평균은 3건부터 내도록 고쳤다.

6번과 같은 종류다. `남은일수 < 0`을 안 봤고, `기한 - 버린날짜`의 부호를 안 봤다. 둘 다 화면에 숫자가 뜨고 나서야 알았다.
